Es gibt weder einen Shell-Escape noch einen Befehl für rohe IRC-Injektion, eine Plugin-/Skript-Engine oder automatische CTCP-Antworten. Befehle werden durch einen Parser mit Positivliste zugelassener Aktionen verarbeitet. Unbekannte Aliase führen zu Fehlern, statt eine Netzwerkaktion zu erraten. Eingehende Protokollfelder, UTF-8, Nicknames, Ziele und Parameterzahlen haben ausdrückliche Grenzen. Bei der Anzeige werden Terminal-Steuerzeichen und unsichere Formatierung entfernt; LIST-Themen werden vor der Übernahme in den Verzeichnis-Cache bereinigt.

Das Ausgabelimit umfasst Befehlssyntax, Ziel, Relay-Identität und Aktionsrahmen. Kleinere gültige LINELEN-Werte des Servers verringern dieses Limit. Aufteilungen erhalten vollständige UTF-8-Zeichen. Mehrere Nachrichten erfordern gesonderte Zustimmung; bracketed paste kann das eigene Senden nicht bestätigen. Die Chat-Warteschlange je Server enthält 64 Einträge mit mindestens 1.2 Sekunden Abstand, hinzu kommt eine separate Steuer-Warteschlange mit 64 Einträgen. Diese Schranken garantieren keine Zustellung und setzen Flood-Regeln des Servers nicht außer Kraft.

Das Programm unterstützt acht Serververbindungen, 32 Ansichten pro Server, 4096 gespeicherte Benutzer je Kanal und 8192 LIST-Einträge. Eine abgeschnittene Mitgliederliste oder ein Verzeichnis ist unvollständig. Trennung oder ausdrückliche LIST-Ablehnung gibt eine ausstehende Anfrage frei, behält jedoch Teil-Einträge im Cache; der Schnappschuss wird nicht als vollständig ausgegeben. Eine neue Anfrage oder explizites Löschen bleibt möglich. Unaufgeforderte Privatnachrichten erzeugen nur unterhalb der automatischen Grenze von acht Dialogen neue Abfrageansichten; weitere Unterhaltungen erscheinen in Server-/mentions-Ansichten. Explizite Dialoge sind innerhalb der gesamten Ansichtsgrenze möglich.

Für gespeicherten Text gelten 8 MiB pro Server und eine Einstellung von 50..5000 Zeilen je Ansicht. Der minimalistische Anzeigestrom begrenzt separat gespeicherte Datensätze auf 2048 und Text auf 512 KiB. Das sind keine Grenzen für gesamten RSS: Entwürfe, Mitgliederlisten, Warteschlangen, Bibliotheken und Verwaltungsaufwand des Allokators verbrauchen zusätzlichen Speicher. Auch ein begrenztes Programm kann durch feindlichen Verkehr viel CPU verbrauchen. ignore-Masken verringern angezeigte Benutzernachrichten, nicht die Arbeit des Empfangens/Parsens; sie sind keine Zugriffsgrenze.

Die ursprünglichen Terminaltasten für Interrupt/Beenden/Anhalten bleiben zugeordnet, aber [input] use_signals=false (Standard) deaktiviert terminalerzeugte Signale, solange der Client das tty besitzt. Ctrl-C/Ctrl-Z brechen ungesendeten Compose/Command-Text ab. Use signals=yes aktiviert die vorhandenen Signalbelegungen des Terminals. Apply wirkt sofort; Save speichert zusätzlich die Einstellung. Ein wörtliches Ctrl-D ist nur bei ausdrücklicher Bindung in Chat oder Befehlszeile ein Programm-Endekürzel. Normales oder behandeltes Beenden stellt Terminalmodi wieder her; SIGKILL kann keine Bereinigung ausführen.

Erkanntes bracketed paste bleibt wörtlicher Text. Vor Erkennung der Öffnungsmarkierung kann der Client Einfügen nicht von normaler Eingabe unterscheiden. Nach erkanntem Ende warten normale Tasten und benutzerdefinierte Aktionen auf einen späteren Eingabeblock und eine Ruhezeit. Das bestätigende Editorfeld oder Formular muss vollständig sichtbar sein; ein fehlerhaftes oder zu kleines Bild zählt nicht als Prüfung. Wiederholte Tasten verlängern die Wartezeit. Größenänderung oder erneutes Anhängen löscht diese Anzeigebestätigung. Einzelnes Escape hat 500 ms Aufschub; unvollständige Folgen erlauben 1000 ms zwischen Fortsetzungsbytes, während das Netzwerk weiterläuft. Eine verspätete Öffnungsmarkierung kann als Escape wirken (Hintergrundwechsel aus dem minimalistischen Log). Nach Beginn der Erfassung haben getrennte Schlussmarkierungen kein Timeout zwischen Bytes. Unmarkiertes Einfügen besitzt keine entsprechende Sicherheitsbarriere.
