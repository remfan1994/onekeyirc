ZNC AND SOJU BOUNCER CONNECTIONS
Current guide: vipirc 0.7.36 / onekeyirc 0.1.35

WHAT THIS CONNECTION DOES

Your local client connects to the bouncer; the bouncer separately maintains
its upstream IRC connection. Use one saved client profile per upstream network.
The bouncer account/network names are not your IRC nickname or NickServ login.
The local --sessions registry is also separate from bouncer networks.
This guide applies to onekeyirc, vipirc -i and full vipirc.

QUICK SETUP

Open /panel, select a server profile, and choose connection type znc or soju.
In the full vipirc interface the same fields are in Settings. Enter:

  - The bouncer hostname and its assigned TLS port.
  - Your IRC nickname.
  - Your bouncer username.
  - The name of an upstream network already configured in that bouncer.
  - An optional stable client name, such as laptop or desktop.
  - The bouncer password source selected by the panel.

Use the provider's hostname and port. IRCNow's ZNC examples use TLS port
31337, but the client does not assume that every bouncer listens there.
Use one profile per upstream network. Account/network/client components
support up to 63 ASCII letters, digits, '.', '_' and '-'. Account and network
are required; the optional client name identifies this device to the bouncer.
Use a different stable client name on another device if separate buffers are
desired and supported by the bouncer's configuration.

At Finish, review the settings and select Save and connect, Save only,
Connect once or Apply only. Earlier answers do not save or connect.
Quickstart remains the shorter direct-IRC setup; use /panel for bouncers.

ZNC uses the existing server-password source. Enter the password only.
The client constructs user@client/network:password in memory (or
user/network:password without a client name). No manual combined login
string is necessary in this mode. SASL settings must be cleared because
the bouncer's own upstream authentication is managed separately.

soju uses the existing SASL authentication-password source. Its identity is
user/network@client (or user/network without a client name). The client
requires successful SASL PLAIN before accepting registration. auth_user is
empty in this mode because the bouncer fields supply the identity.

Use the bouncer account's password, not an upstream NickServ password.
Both modes require verified TLS. The existing private-file and GPG loaders
are reused. The panel can use an existing encrypted file or create one with
an existing local public key. GPG must be able to decrypt without an
interactive prompt when the client later connects. Passwords are not placed
in shell command arguments by this workflow.

Changing a bouncer endpoint, account, network, client identity or CA selection
in the setup form clears its old credential draft. Re-enter the correct
source for the changed identity. Applying or saving an incomplete credential
combination is rejected. Cancelling setup leaves the active profile intact.

CONFIGURATION EXAMPLES

examples/bouncer-znc.ini and examples/bouncer-soju.ini are partial profiles
that use ordinary defaults for omitted settings. They work with either
client's configuration namespace. Replace their example hostname, port,
nickname, account, network and credential path before use. Store a config in
a private directory and give it mode 0600. These examples use absolute paths
to avoid launch-directory dependence. Relative paths resolve from the process
working directory, not the config directory. Paths are literal; there is no
shell expansion of ~ or variables.

ZNC:

  [connection]
  server=example.ircnow.org
  port=31337
  tls=true
  nick=mynick
  auth=none
  server_password_gpg_file=/home/me/.config/onekeyirc/credentials/bouncer.gpg

  [bouncer]
  type=znc
  username=myaccount
  network=ircnow
  client=laptop
  automatic_away=false

soju:

  [connection]
  server=bouncer.example.org
  port=6697
  tls=true
  nick=mynick
  auth=sasl
  password_gpg_file=/home/me/.config/onekeyirc/credentials/bouncer.gpg

  [bouncer]
  type=soju
  username=myaccount
  network=ircnow
  client=laptop
  automatic_away=false

Choose exactly one password source. For ZNC these are server_password_file,
server_password_gpg_file or server_password. For soju they are password_file,
password_gpg_file or password. Inline passwords remain an explicit existing
option in a private config; their bytes after '=' are literal. File and GPG
contents contain only the password. ZNC's combined identity and password must
fit the client's existing bounded IRC PASS frame.

[connection] username is the ordinary IRC USER field. [bouncer] username is
the bouncer account used in the derived login. Leave auth_user empty in both
explicit bouncer modes. ZNC requires auth=none and no SASL password source;
soju requires auth=sasl and no server-password source. These constraints are
checked together, so a stale direct-IRC credential cannot silently be reused.

Use the system trust store when possible. A custom ca_file selects a trusted
PEM bundle: it must resolve to a nonempty regular file no larger than 16 MiB.
CA symlinks are allowed; private config and credential symlinks are refused.
--check-config checks the profile's syntax and combinations, not CA contents,
credential accessibility/decryption or whether the bouncer accepts the login.

The default bouncer type is none. Old direct-IRC configurations and manually
constructed legacy ZNC PASS values remain usable in that mode. To migrate a
legacy combined PASS into explicit znc mode, change its credential source to
contain only the password and fill the new identity fields.

CHANNELS, AWAY STATE AND RECONNECTING

The bouncer restores its current channel memberships after login. These
clients accept those restored JOINs and do not replay their saved channel
list in bouncer mode. This avoids undoing a PART made from another device.
Use /join and /part while connected to change the bouncer's memberships.
/autojoin shows this policy; its add/remove/clear mutations are rejected.
Existing explicitly configured startup commands still run; an explicit
startup /join is therefore a deliberate exception.

The bouncer profile's automatic_away setting defaults to false. This prevents
one idle or backgrounded device from imposing away status on other devices.
Set it to true only if this profile should follow the application's existing
idle/background-away preferences. Manual /away and /back remain available.
This setting does not change the other profiles' presence preferences.

--reconnect retains the existing bounded retry policy. Credential rejection
does not trigger a rapid retry loop. Reconnecting creates a new downstream
session; the bouncer remains responsible for its upstream IRC connection.
--detach-session and --close-session continue to control this local client
worker. They do not administer or terminate the remote bouncer service.

CONTROL COMMANDS

  /znc
  /znc ListNetworks
  /znc Connect
  /msg *status Help
  /msg *module COMMAND

  /soju
  /soju network status
  /msg BouncerServ help

Use the matching control shortcut only on a connected profile of that type.
No argument asks the bouncer for its own help. Module names refer to modules
actually enabled by your ZNC administrator. Control text must fit one IRC
message and is paced through the ordinary outgoing queue. It is not silently
split into several control commands. /cancel can remove an unsent command.

Control commands are excluded from input history and local message echoes.
Incoming copies addressed to the bouncer service are suppressed even if their
source is an older nickname from replay or an unrecognized batch reference.
Replies appear in the server view (select it with /server) and are excluded
from optional persistent logs. Text typed into an ordinary command editor
can still be visible on the terminal while being composed. The bouncer
receives the commands and may have its own logging policy. Never assume a control command is private
from the bouncer administrator.

PLAYBACK AND RESOURCE USE

The client negotiates server-time, batch, multi-prefix, and ZNC self-message
support when offered, plus SASL when required. It does not request
echo-message, draft/chathistory or znc.in/playback capabilities. Those would
require different echo or history-request behavior. Ordinary pushed buffers
are supported without implementing an on-demand archive browser.

Recognized history batches stream into the existing bounded scrollback.
There is no second unbounded backlog copy. At most 16 batches with 64-byte
references can be active at once; malformed, inconsistent or over-limit
framing disconnects with a diagnostic.
Nested/interleaved batches inherit known playback boundaries. Unknown batch
references are treated conservatively as display-only.
Original valid server timestamps are displayed in UTC; malformed timestamps
fall back to the normal local-time display. Remote time never controls
timeouts, reconnect backoff or outgoing pacing.

Replayed private messages sent by your own nickname go to the conversation
with their recipient. Known history does not change current memberships or
presence, create fresh mention alerts, answer CTCP requests or activate DCC
offers. Replayed own messages do not replace the local last-sent catch-up
anchor. Ordinary live messages continue through the existing paths.

Older servers that do not identify playback batches cannot supply the same
history boundary. A timestamp alone is not treated as proof that a message
is historical. The client does not promise to retrieve history the bouncer
does not retain, deduplicate arbitrary replay across fresh processes, or
automatically discover all of an account's networks.

TROUBLESHOOTING

TLS or hostname failure:
  Check the provider's assigned hostname/port, system clock and CA store.
  An IP address needs a certificate valid for that IP. Do not replace the
  assigned host with an unrelated alias or disable verification to send a
  password. A custom CA must be trusted and meet the regular-file/size rules.

Credential or SASL failure:
  Check the chosen bouncer type, account, existing network name and exactly
  one matching password source. Enter only the bouncer password in its file.
  Use /autoauth for local source-path/status information; it does not read or
  print the secret. Unlock a protected GPG key outside the client and retry.
  Required SASL PLAIN must actually be offered by a soju endpoint.

No channels, missing backlog or the wrong network:
  Inspect the selected profile and the bouncer's own network status/help.
  /znc ListNetworks and /soju network status query their respective services.
  /join changes current membership; /autojoin does not overwrite bouncer
  state. The bouncer decides what it stores and pushes. A new local worker
  does not automatically import an old transcript as a bouncer archive.

Unexpected away state:
  automatic_away=false suppresses this profile's automatic client presence.
  Manual commands, another attached device and the bouncer's own policy can
  still change upstream away. Inspect those separately.

Changed settings appear not to apply:
  Save persists a profile; it does not replace a live connection. An automatic
  retry retains the interrupted connection's snapshot. Explicitly disconnect
  and connect to apply staged endpoint/authentication changes.

Unknown module or service command:
  /znc and /soju are guarded one-message shortcuts to those services. Available
  modules, administration rights and exact service commands belong to the
  running bouncer. Ask its help; this client does not implement the bouncer's
  administration features or create accounts/networks automatically.

Busy local resume after SSH loss:
  Use PROGRAM --sessions, --detach-session NUMBER, then --resume NUMBER.
  See doc/SESSION-CONTROLS.txt. These commands preserve or close the local
  worker; they do not repair or stop the bouncer daemon.

VERIFICATION AND SCOPE

make check-bouncers runs configuration, shared core, command and setup
regressions, duplicate SASL declarations, old-nickname control privacy and an
independent bounded CAP/BATCH state model. make check-bouncers-sanitize
builds the focused sanitizer tests.
make check-bouncers-terminal runs the real executable through verified
loopback TLS and PTYs against private ZNC/soju-shaped protocol fixtures.
make check-efficiency includes stream traversal and existing roster/history
checks. Exact executed results and platform limits are recorded in
doc/BOUNCER-VALIDATION.txt and doc/BOUNCER-TEST-RESULTS.json.

The subsequent security pass is recorded in doc/SECURITY-REVIEW-0.7.30-0.1.29.txt
and doc/SECURITY-BOUNDARY-RESULTS.json for those named source versions.
This guide was refreshed for the documentation release; its documentation
checks are recorded in doc/DOCUMENTATION-VALIDATION.txt. Historical evidence
has not been relabeled as a new live-bouncer or security test run.

The protocol fixtures are not a claim that real ZNC/soju packages or an
IRCNow account were exercised. The full ncurses interface and native OpenBSD
require the target-platform checks identified in the validation report.
The earlier security fixes and their separately scoped reports are retained.
