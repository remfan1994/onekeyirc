SECURITY FOLLOW-UP AND TERMINAL POLICY REVIEW
Date: 2026-11-16 UTC
Releases: onekeyirc 0.1.26 and vipirc 0.7.27
Compared with: onekeyirc 0.1.25 and vipirc 0.7.26

RESULT AND SCOPE

The executed release gates passed. Confirmed findings were fixed in the
shared core and both affected frontends. The full requested local notice
and default-off terminal signal override are included. This is a bounded
source review with reproducible regressions, not a security certification.

Final gate groups: 62 PASS, 1 UNAVAILABLE, 0 FAIL.
The unavailable group is native AF_UNIX session lifecycle; additional
full-curses, native OpenBSD, real GnuPG and leak-scanning limits are explained
below. A passing group may contain several C binaries or terminal cases.
No full unrestricted make check or native OpenBSD pass is claimed.

The threat model includes hostile IRC/server text, terminal-control bytes,
malformed DCC traffic and offers, resource pressure, and other local UIDs.
The account itself, administrator/kernel, executable, terminal, TLS library
and trust store remain trusted. Local tests used an offline simulator,
private temporary files, real PTYs and loopback TCP; they did not contact
the public IRC network or modify a user's running worker.

The prior audit remains in doc/AUDIT-2026-11-15.txt. Earlier controls for
non-destructive terminal detach, whole-session close, saved interface choice,
wrapped chat, history recall and managed hangup handling remain included.

HOW TO READ THE EVIDENCE

FOLLOWUP-TEST-RESULTS.json contains exact commands, results, output, source
and binary hashes, source diffs, and scoped development snapshots. Evidence
paths named below are keys in that file's evidence_documents mapping, relative
to irc-security-followup-validation/. New regression sources are in tests/.
Expected baseline failures and repaired fixture assumptions are kept separate
from final release results; they are not silently converted into passes.

1. Confirmed availability problem: failed automatic away

A server can advertise a small valid LINELEN, making an enabled automatic-
away message too long to queue. The old code left its automatic-away timer
expired after that failure, so the event loop repeatedly returned a zero
timeout and attempted the same impossible send. Temporary control-queue
exhaustion could also trigger the failed-attempt path. This requires the
server's advertised limit and an applicable local away configuration;
ordinary channel text does not set LINELEN.

The candidate schedules a one-second retry deadline, includes it in poll
scheduling, and resets it after success, local activity or reconnect. Manual
away keeps priority, and normal networking remains available during the wait.
Deterministic tests cover the exact retry boundary, queue/line-limit recovery,
PING/PONG, reconnect/activity reset and absence of duplicate successful AWAY.

The unchanged baseline produced 1,000 zero timeouts in 1,000 deterministic
iterations without advancing time. A separate three-second real-worker
comparison measured about three worker CPU seconds in the baseline and no
observable CPU-tick increment in the candidate, at 10 ms sampling resolution.
Both answered all nine measured PINGs. This is a short diagnostic comparison,
not a long-duration reliability claim or a claim of literally zero CPU use.
That real worker used fixture-managed detach/reattach, not native session IPC.

Evidence: network/final-findings.txt, network/presence-baseline.log,
network/presence-fixed.log, network/results.json, dcc/presence-review.txt,
dcc/presence-build-results.json and dcc/presence-results.json.

2. Confirmed privacy problem: credential text in command recall

The core accepted private authentication verbs after repeated or separated
leading colons, while the minimalist history filter stripped only one colon.
Accepted examples such as ::IDENTIFY, : : IDENTIFY and : LOGIN after /msg or
/privmsg could therefore enter that frontend's in-memory recall history.
The candidate aligns this normalization with the core classifier.

A second mismatch affected both frontends. A logical command could start
with ordinary HELP text, fill one IRC payload, then start the next payload
with IDENTIFY. The core recognized the resulting wire plan as private, but
the old history filters inspected only the original command's first word.
Baseline tests reproduced actual retention, including the full frontend's
production send/remember path. This demonstrates in-process command-recall
retention; it does not demonstrate unintended-peer transmission or a disk
credential leak.

Both histories now use the exact accepted message plan as well as syntax
classification. The shared helper validates bounded logical/wire slices and
fails closed on malformed plans. Direct and review paths preserve ordinary
history and canonical command-name counts while excluding recognized private
plans. Cancellation, failed sends and subsequent commands cannot reuse an
obsolete pending plan. Independent read-only review found no additional
stale-plan/text mismatch in those paths.

This remains a recognizer for known credential forms, not a general detector
of secrets in arbitrary prose or unknown custom authentication commands.
The user's editable draft and other process memory are separate from recall;
this change does not promise to erase every copy of a secret.

Evidence: network/history-baseline.log, network/ui-history-baseline.log,
network/history-fixed.log, network/history-flow-normal.log,
network/ui-history-normal.log, network/results.json and
network/final-findings.txt. Focused normal and ASan/UBSan gates passed; leak
scanning was disabled. The full-UI fixture extracts unchanged production
blocks and uses real application/editor/prompt code with inert presentation
callbacks. It does not validate curses rendering or terminal dispatch.

3. Confirmed local integrity problem: stale catch-up anchor

/catchup previously retained the byte offset of the last local sent record.
If an owned private log was rotated/replaced, another record at that offset
with the same channel prefix could be mistaken for the original anchor.
The baseline reproduction used real private-file rotation and the production
begin_catchup path. No hostile-network-only trigger was demonstrated.

The candidate binds a successfully appended anchor to the original device,
inode, exact record length and a checksum of the complete record. Reopening
catch-up rechecks private-file policy, bounds, identity and record contents.
Ordinary appends remain valid. Replacement, truncation or a changed anchor
uses the original retained in-memory history if available, otherwise the
existing unavailable-anchor notice. It does not claim continuity with an
unrelated record. The reader retains its bounded storage and pinned end.

Regressions cover an identical-content replacement inode, same-channel
replacement, same-inode and same-size changes past the first 1 KiB, append,
growth, truncation and the original rendered memory fallback. Normal and
ASan/UBSan tests passed, and a second reviewer found no further bounds or
identity defect. FNV-1a is accidental-change detection, not authentication.
This is not an immutable transcript and does not protect against trusted
same-UID rewriting, including changes that preserve the exact anchor.

Evidence: dcc/probe_catchup_anchor.c, dcc/baseline-catchup-anchor.log,
local/local-review-results.json, local/anchor-normal-results.json,
local/anchor-sanitize-results.json and dcc/notice-presence-review.txt.

5. Terminal signal policy and local session notice

The new configuration-only preference is:

  [input]
  force_terminal_signals=false

False or omission preserves the terminal's inherited ISIG state; it does not
disable signals that the user already enabled. True enables ISIG while
retaining the inherited interrupt, quit and suspend character mappings.
Neither mode assigns Ctrl-C or Ctrl-Z as a new client key binding. The primary
application configuration owns the setting across server profiles. Saved
true/false values round-trip, malformed values are rejected transactionally,
and failed saves leave current and future profiles unchanged. Four isolated
strict config/client/application tests passed. Terminal runtime results are recorded separately from these config checks.

Evidence: local/terminal-signals/results.json and
local/terminal-signals/mirror.json; dcc/terminal-signals-results.json and
dcc/terminal-signals-baseline-final-results.json;
network/terminal-signals-results.json. The baseline default -isig failure
was reproduced. Final normal real-shell tests pass all three policy cases
in onekeyirc and the vipirc -i harness, including mapped suspension at the
welcome/composer,
retained draft/caret and seven exact pre-shell terminal/descriptor restorations
per tested minimalist executable. An initial shell-fixture mistake was corrected without relaxing
assertions: terminal remappings must be installed in the parent shell before
the job starts, so fg preserves the intended parent settings.

The full curses helpers separately pass eight policy/mapping combinations,
program-mode restoration, inactive stop, fresh entry after shell changes,
and five initialization failures. These tests use exact production helpers
and actual PTY termios, with curses calls simulated. They do not run a full

7. Retained design limits and safe upgrade

Other local UIDs and hostile remote bytes are in the review threat model;
the same UID, administrator/kernel, installed executable, terminal, TLS
library and trust store remain trusted. Account-private IPC is not isolation
from a compromised account. The client has no process sandbox or privilege
separation. Continue using a dedicated ordinary account, verified TLS,
private configuration/credential paths and no setuid/setgid installation.
Avoid forwarding an SSH agent or exposing unrelated secrets to that account.

Persistent logs remain opt-in, access-controlled plaintext, not encrypted or
authenticated transcripts. Known credential/service filtering is incomplete
for arbitrary secrets or unknown services. Logs survive exit; each active
log has a 16 MiB stop limit, not an archive or disk-space quota. Existing logs
are not automatically deleted or rotated. Regular-file I/O can still stall
on underlying storage. Enabling logging is a deliberate retention decision.

Classic DCC remains unencrypted and unauthenticated independently of IRC TLS.
An accepted offer can reach its advertised endpoint, including a private
address; a nickname does not authenticate the peer. Files are not executed
automatically, but source contents can change while streaming. For ordinary
unattended IRC idling, leave DCC unused; no extra public inbound port is
needed. Per-file/transfer bounds do not provide a host-wide storage quota.

Installing a replacement executable does not replace a running worker.
--resume attaches to the old process and --detach-session releases a terminal
while preserving that process. Neither applies these fixes. Save desired
configuration and account for drafts, queued messages and active transfers
before a controlled restart. Inspect --sessions and use the documented
--close-session ID workflow when ready to end the old worker, then verify
the installed --version and start a fresh worker. Closing ends its IRC
connections and retained in-memory session; it is not just a detach.
An unsupported/unresponsive old worker must not be represented as closed.

Older executables can reject the new config key after a new release saves
it. Preserve a private pre-upgrade config copy if rollback is required.
Do not disable TLS verification, relax private permissions, blindly signal
a job number as a PID, or remove live registry files to force an upgrade.
On the actual host, verify session list/detach/resume/close, SSH loss and
reconnect, terminal restoration/remapped signals and normal PING handling.
Exercise actual full curses and rc.d behavior separately when used. No live
IRCNOW connection, user service, or deployment was modified by this review.

These cautions preserve the baseline doc/AUDIT-2026-11-15.txt operational
upgrade section and doc/SECURITY-REVIEW.txt deployment guidance.

8. Final validation and packaging

The standalone release was built with strict C11 warnings promoted to errors,
FORTIFY_SOURCE=2, stack-protector-strong, format-security checks and PIE; Linux
linking requested RELRO, immediate symbol binding and a non-executable stack.
ASan/UBSan builds use halt-on-error and retain the explicit no-leak-scan limit.

Normal gates cover the security suite, efficiency checks, session CLI/control
boundaries, managed hangup/detach fixtures, application/credential/editor/DCC
units, CLI and embedded manual consistency, offline/live terminal behavior,
setup and asynchronous helpers, reconnect/autojoin, rename, wrapping, pinned
destinations, catch-up, slow terminal handling and retained history.

Sanitizer gates cover the security and session-control suites, notice delivery,
credential child lifecycle, DCC injected failures, real automatic-away retry
availability, wrapping, reviewed-message availability and terminal signal
policy. vipirc -i uses real main/core/minimalist code with aborting unused
curses entry points. Full UI history and terminal policy have separate exact
production-boundary tests; presentation/curses substitutions are disclosed.
The vipirc Makefile's non-curses history and CLI test variants were also built
and executed normally and with ASan/UBSan.

The 90-second hostile-idle gate exercises hostile display payloads and malformed
UTF-8 inside correctly framed IRC traffic, bounded state, resource behavior, continued PING handling and process cleanup.

9. Deployment dependencies

The observed test host was Linux x86_64, GCC 14.2.0 and OpenSSL 3.5.7. The client
uses the system TLS implementation; these source changes do not update a VPS's
kernel, SSH server, terminal or TLS packages. Official OpenSSL release notes
list security fixes newer than the test library. Check the actual deployment's
supported OS/TLS update status independently; this report does not establish
that the running VPS has those updates.

Primary vendor references checked during this review:
  https://www.openssl-library.org/news/openssl-3.5-notes/index.html
  https://openssl-library.org/news/vulnerabilities/
  https://www.openbsd.org/stable.html
  https://www.openbsd.org/errata80.html

The source's verified-TLS defaults, certificate/hostname verification and
credential policies should remain enabled. Use the documented session controls
for a deliberate restart after saving desired settings; attaching to an older
worker cannot install these changes into that running process.
